- [ ] **[medium · ?]** Color "orange" plays the food clip "Can you find an orange?"
    - **where:** app.js 1091-1092 (textToAudioKey regex) + 118 (colors speakPrompt)
    - **what:** textToAudioKey's find-prompt regex /^Can you find (?:a |an |some |something )?(.+)\?$/ strips the leading 'something ' from the colors prompt, so 'Can you find something orange?' (colors) collapses to the SAME key as 'Can you find an orange?' (food): both -> 'find-orange'. There is no find-something-orange.mp3 on disk (verified: only find-orange.mp3 exists, and sw.js's colors block at lines 165-173 deliberately omits find-orange). So the Colors-category orange item plays the FRUIT clip. 'orange' is the only word shared between the food and colors lists, so it is the only collision. preloadAllAudio also warms the food clip under 'find-orange', so the wrong clip is the one cached.
    - **repro:** As a premium user pick Colors on Medium or Hard (orange is d:2, excluded on Easy). When the orange swatch comes up, the child sees 🟠 but hears 'Can you find an orange?' (the fruit).
    - **fix:** Give the colors prompt a distinct key. Easiest: add an explicit map entry in textToAudioKey, e.g. "'Can you find something orange?': 'find-something-orange'", record that clip, and add it to preloadAllAudio + sw.js precache (bumping CACHE_VERSION/?v together). Or namespace all color prompts (find-color-<x>).

- [ ] **[medium · ?]** Interrupting a clip fires the interrupted clip's onEnd callback
    - **where:** app.js 1022-1028 (playBuffer) and 1101 (speak)
    - **what:** When a new clip starts, playBuffer calls currentAudioSource.stop() (1022) but the stopped source's onended STILL fires asynchronously. Its handler is 'if (currentAudioSource === source) currentAudioSource = null; if (onEnd) onEnd();' (1026) - the guard only protects the null-assignment, NOT the onEnd() call. - [ ] **[medium · ?]** Stale playKeyWhenReady fallback can speak the previous prompt over the current clip
    - **where:** app.js 1121-1134 (playKeyWhenReady), 1096-1117 (speak)
    - **what:** speak() does not invalidate playKeyWhenReady timers/promises from a previous, superseded call.
